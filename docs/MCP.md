# Braze MCP

## Что это за папка

В этой папке собрана практическая документация по работе с `Braze MCP` в текущем окружении Codex.

Документ нужен для двух задач:

1. объяснить человеческим языком, что такое `MCP` и зачем он вообще нужен;
2. зафиксировать, что именно сейчас реально доступно в `Braze` через MCP с текущим ключом из секретов.

Этот файл описывает не абстрактные возможности Braze API вообще, а именно то, что было подтверждено в данном окружении на момент проверки.

Дата проверки: `2026-03-19`

---

## Что такое MCP простыми словами

`MCP` расшифровывается как `Model Context Protocol`.

Если говорить совсем просто, это стандартный способ дать AI-агенту доступ к внешним системам не через «угадывание» и не через ручное копирование данных, а через строго определенные инструменты.

Без MCP агент в чате умеет:

- отвечать текстом;
- анализировать локальные файлы;
- помогать с кодом и SQL;
- делать выводы из уже переданной информации.

Но без MCP агент сам по себе не знает:

- какие кампании есть в Braze;
- какие сегменты существуют;
- какие canvases созданы;
- какие события есть в системе;
- какие атрибуты пользователей доступны;
- какие scheduled broadcasts стоят в очереди;
- какие каталоги и шаблоны лежат в Braze.

Чтобы получить эти данные, агенту нужен «мост» к внешней системе. Таким мостом и является MCP.

---

## Что MCP делает на практике

В практическом смысле MCP-сервер:

1. знает, как подключиться к внешней системе;
2. знает, какие операции в этой системе разрешены;
3. принимает от агента структурированный запрос;
4. идет во внешний сервис;
5. возвращает назад структурированный ответ.

То есть агент не «ходит в Braze как человек», а вызывает готовые функции вида:

- `get_campaign_list`
- `get_segment_list`
- `get_canvas_details`
- `get_custom_attributes`

У каждой такой функции есть:

- имя;
- описание;
- набор параметров;
- ожидаемая структура ответа.

Это важно, потому что агент работает не с «сырой магией», а с понятным интерфейсом.

---

## Как это связано с Braze

`Braze MCP` в данном окружении — это набор функций, через которые агент может читать данные из Braze.

По сути, это прослойка между:

- агентом Codex;
- секретами и ключом доступа;
- конкретными endpoint-ами Braze API.

Когда агент вызывает функцию вроде `get_campaign_list`, происходит логически следующее:

1. MCP берет настройки подключения;
2. использует ключ из секретов;
3. отправляет запрос в Braze API;
4. получает ответ;
5. возвращает этот ответ агенту уже в структурированном виде.

Преимущество в том, что человеку не нужно:

- руками писать HTTP-запросы;
- вспоминать URL нужного endpoint-а;
- подставлять headers;
- парсить JSON вручную;
- держать в голове все детали аутентификации.

## Что такое «функции MCP»

У Braze MCP есть набор экспортированных функций. Их можно воспринимать как безопасные «кнопки действий».

Например:

- одна функция возвращает список кампаний;
- другая возвращает детали конкретной кампании;
- третья возвращает time series по campaign performance;
- четвертая показывает список сегментов;
- пятая возвращает custom attributes;
- шестая показывает scheduled broadcasts.

Важно понимать:

- наличие функции в MCP еще не гарантирует, что текущий ключ имеет к ней доступ;
- часть функций может быть объявлена в MCP, но быть недоступной из-за прав в Braze;
- часть функций может требовать дополнительные идентификаторы, например `campaign_id`, `canvas_id`, `segment_id`, `send_id`, `app_id`, `content_block_id`.

Поэтому есть два уровня проверки:

1. функция существует в MCP;
2. функция реально работает с текущим ключом и текущими данными.

## Что было проверено в этом окружении

На момент проверки MCP-сервер Braze экспортировал `38` функций.

Далее были сделаны безопасные `read-only` проверки, чтобы понять:

- какие функции точно работают;
- какие функции явно запрещены текущим ключом;
- какие функции не удалось полноценно проверить без дополнительных идентификаторов.

Проверка делалась без изменения данных в Braze.

То есть проверялись только сценарии чтения:

- списки;
- детали объектов;
- метрики;
- time series;
- справочники;
- шаблоны;
- content blocks;
- planned broadcasts.

## Общий вывод

Текущий `Braze MCP` в этом окружении работает.

С текущим ключом из секретов уже подтвержден широкий `read access` к основным сущностям Braze:

- campaigns;
- canvases;
- segments;
- custom events;
- custom attributes;
- KPI / analytics series;
- content blocks;
- email templates;
- catalogs;
- scheduled broadcasts;
- часть purchase analytics.

При этом есть как минимум две группы функций, к которым текущий ключ доступа не имеет:

- preference centers;
- CDI integrations.

## Что можно делать через этот MCP уже сейчас

Ниже перечислено не «вообще всё теоретически», а то, что уже подтверждено практической проверкой.

### 1. Смотреть список кампаний Braze

Подтвержденная функция:

- `get_campaign_list`

Что это дает:

- получить список кампаний;
- увидеть `campaign_id`;
- увидеть название кампании;
- увидеть дату последнего редактирования;
- понять, какие теги проставлены;
- отличить API campaign от не-API campaign.

Когда это полезно:

- найти нужную кампанию по имени;
- получить `campaign_id` для последующих запросов;
- быстро понять, какие email / push / WhatsApp кампании есть в рабочем пространстве.

### 2. Смотреть детальную информацию по конкретной кампании

Подтвержденная функция:

- `get_campaign_details`

Что это дает:

- увидеть метаданные кампании;
- узнать, включена ли она;
- понять, архивная ли она;
- увидеть schedule type;
- увидеть используемые каналы;
- посмотреть теги и команды;
- посмотреть message variations;
- посмотреть subject, body, from;
- увидеть conversion behaviors.

Когда это полезно:

- разбирать конкретную кампанию;
- проверять настройки кампании;
- понимать, какие content blocks или тексты участвуют;
- анализировать, что именно было настроено в email-вариациях.

### 3. Получать временной ряд метрик по кампании

Подтвержденная функция:

- `get_campaign_dataseries`

Что это дает:

- получить статистику по дням;
- смотреть отправки;
- смотреть opens;
- смотреть unique opens;
- смотреть clicks;
- смотреть unsubscribes;
- смотреть bounces;
- смотреть delivered;
- смотреть revenue;
- смотреть conversions;
- смотреть разбивку по variation.

Когда это полезно:

- быстрый performance review кампании;
- daily monitoring;
- подготовка аналитических заметок по результатам кампании;
- проверка, были ли вообще отправки и реакция аудитории.

### 4. Смотреть список Canvas

Подтвержденная функция:

- `get_canvas_list`

Что это дает:

- список canvases;
- `canvas_id`;
- название;
- дату последнего редактирования;
- теги.

Когда это полезно:

- найти нужный canvas;
- получить `canvas_id` для последующих запросов;
- ориентироваться в существующих journeys / flows.

### 5. Смотреть детали конкретного Canvas

Подтвержденная функция:

- `get_canvas_details`

Что это дает:

- метаданные canvas;
- draft / enabled / archived status;
- schedule type;
- channels;
- variants;
- steps;
- messages внутри steps.

Когда это полезно:

- разбирать логику journey;
- понимать структуру шагов;
- проверять, какие сообщения реально входят в flow;
- анализировать текущую конфигурацию canvas.

### 6. Получать series и summary по Canvas

Подтвержденные функции:

- `get_canvas_data_series`
- `get_canvas_data_summary`

Что это дает:

- статистику по дням;
- entries;
- conversions;
- revenue;
- агрегаты по canvas;
- при наличии данных — разрезы по variant / step.

Когда это полезно:

- смотреть performance journeys;
- сравнивать активность canvas во времени;
- проверять, были ли входы пользователей в поток;
- быстро получать performance snapshot.

Важно:

Если в указанном интервале нет активности, функция может вернуть `success`, но данные будут пустыми или с `notice`, что данных в периоде нет. Это не ошибка доступа.

### 7. Смотреть список сегментов

Подтвержденная функция:

- `get_segment_list`

Что это дает:

- список сегментов;
- `segment_id`;
- название;
- включен ли analytics tracking;
- теги.

Когда это полезно:

- найти нужный сегмент;
- понять, какие сегменты уже существуют;
- получить `segment_id` для дальнейших запросов;
- оценить, какие сегменты аналитически трекаются.

### 8. Смотреть детали конкретного сегмента

Подтвержденная функция:

- `get_segment_details`

Что это дает:

- название сегмента;
- дату создания и обновления;
- human-readable описание фильтров;
- текстовое описание;
- теги;
- команды.

Когда это полезно:

- понять бизнес-логику сегмента без ручного захода в UI;
- сверить, что именно означает сегмент;
- документировать сегменты;
- проверить, какой фильтр лежит за конкретным названием.

### 9. Смотреть динамику размера сегмента

Подтвержденная функция:

- `get_segment_data_series`

Что это дает:

- размер сегмента по дням;
- изменение размера во времени.

Когда это полезно:

- мониторить рост / падение сегмента;
- проверять, как сегмент меняется перед отправкой;
- оценивать стабильность audience size.

### 10. Смотреть список custom events

Подтвержденные функции:

- `get_events_list`
- `get_events`

Практически подтверждена работоспособность списка событий через `get_events_list`.

Что это дает:

- список кастомных событий;
- ориентир, какие event names реально существуют в Braze.

Когда это полезно:

- искать event для аналитики;
- проверять правильное имя события;
- подготавливать запросы на event series.

### 11. Получать time series по custom event

Подтвержденная функция:

- `get_events_data_series`

Что это дает:

- число occurrences выбранного события по дням или часам;

Когда это полезно:

- сравнение активности event;

### 12. Смотреть список custom attributes

## Что сейчас явно недоступно по правам

Ниже перечислены функции, по которым был получен явный отказ доступа.

### 1. Preference Centers

Проверенная функция:

- `get_preference_centers`

Результат:

- `403 Forbidden`

Что это означает:

- MCP-функция существует;
- сам MCP жив;
- но текущий ключ из секретов не имеет права читать список preference centers.

Следствие:

- нельзя надежно работать с этой областью через текущий ключ;
- любые сценарии вокруг preference centers потребуют другой ключ или другого уровня доступа.

### 2. CDI Integrations

Проверенная функция:

- `list_integrations`

Результат:

- `403 Forbidden`

Что это означает:

- доступ к CDI integrations текущим ключом закрыт.

Следствие:

- нельзя через этот ключ смотреть список integration jobs;
- соответственно, `get_integration_job_sync_status` тоже практически недоступен для рабочей эксплуатации, если не появится другой ключ или заранее известный `integration_id` с подходящими правами.

## Что не было полностью проверено, но может работать

Ниже функции, которые не удалось полноценно подтвердить не потому, что MCP сломан, а потому, что для них нужны дополнительные идентификаторы или входные данные.

### Требуют конкретный ID объекта

- `get_send_data_series`
  Нужен `campaign_id` и `send_id`.

- `get_content_block_info`
  Нужен `content_block_id`.

- `get_email_template_info`
  Нужен `email_template_id`.

- `get_catalog_item`
  Нужен `catalog_name` и `item_id`.

- `get_catalog_items`
  Нужен `catalog_name`.

- `get_preference_center_details`
  Нужен `preference_center_id`, но list уже закрыт по `403`.

- `get_sdk_authentication_keys`
  Нужен `app_id`.

- `get_integration_job_sync_status`
  Нужен `integration_id`, а список integrations закрыт по `403`.

### Требуют user identifiers или subscription identifiers

- `get_subscription_group_status`
  Нужен `subscription_group_id` и один из user identifiers: `external_id`, `email` или `phone`.

- `get_user_subscription_groups`
  Нужен user identifier: `external_id`, `email` или `phone`.

### Требуют дополнительную сущность или ручную донастройку сценария

- `get_catalog_item`
- `get_catalog_items`
- `get_send_data_series`

Их можно проверить дополнительно, если заранее известны конкретные рабочие идентификаторы.

## Что важно понимать про ошибки `400`, `403` и пустые данные

При работе с MCP важно различать разные типы результатов.

### `success`

Это значит:

- функция существует;
- доступ к endpoint есть;
- Braze ответил корректно;
- ответ можно использовать в работе.

### `success`, но данные пустые

Это не обязательно проблема.

Обычно это означает одно из трех:

1. в системе реально нет данных под этот запрос;
2. выбран период без активности;
3. нужны дополнительные фильтры, например `app_id`, `product`, `segment_id`.

Пример:

- `get_quantity_series` может вернуть пустой список;
- `get_revenue_series` может вернуть пустой список;
- это не означает, что доступ сломан.

### `400 Bad Request`

Обычно это значит:

- запрос сформирован неверно;
- переданы неподходящие параметры;
- у endpoint-а более строгие требования к payload.

В этой проверке был важный пример:

- первые вызовы `get_content_blocks` и `get_email_templates` с лишними параметрами дали `400`;
- после вызова без этих параметров функции отработали успешно.

Вывод:

- `400` не всегда говорит об отсутствии доступа;
- иногда это просто вопрос правильной формы вызова.

### `403 Forbidden`

Это уже важный сигнал про права.

Обычно это означает:

- текущий API key не имеет доступа к этой части Braze;
- либо у workspace / ключа нет нужного scope;
- либо этот домен Braze ограничен политикой доступа.

В этой проверке `403` был получен для:

- preference centers;
- CDI integrations.

## Ограничения текущей конфигурации

На данный момент важно помнить несколько ограничений.

### 1. Это в первую очередь read-only использование

В рамках текущей проверки подтверждены именно операции чтения.

В этом документе нет подтверждения, что через текущий MCP и текущий ключ можно:

- создавать кампании;
- обновлять сегменты;
- менять шаблоны;
- запускать рассылки;
- изменять content blocks;
- редактировать canvases.

Если такие задачи понадобятся, их нужно проверять отдельно.

### 2. Не все функции можно проверить без ID

Часть функций становится полезной только после того, как уже найден объект верхнего уровня:

- сначала найти template;
- потом взять `email_template_id`;
- потом уже получать info по нему.

То же самое относится к:

- `content_block_id`;
- `send_id`;
- `catalog_name`;
- `item_id`;
- `app_id`;
- `subscription_group_id`.

### 3. Права зависят от ключа, а не только от MCP

Это один из самых важных принципов.

Наличие функции в MCP означает:

- MCP знает, как этот запрос делать.

Но это не означает:

- что ваш ключ имеет нужные scopes;
- что Braze разрешит доступ;
- что в workspace есть соответствующие сущности;
- что endpoint активирован в аккаунте.

Именно поэтому в документации нужно различать:

- «функция существует»;
- «функция доступна текущим ключом».

## Рекомендуемый способ использования

Если нужно работать с Braze через агента, лучше двигаться так:

1. Сначала понять, какая сущность нужна:
   campaign, canvas, segment, event, template, content block, catalog.
2. Сначала получить список объектов верхнего уровня.
3. Из списка взять нужный ID.
4. Потом вызывать detail / data series / info функции.
5. Если получен `403`, считать это ограничением прав текущего ключа.
6. Если получен `400`, сначала проверить корректность параметров.
7. Если пришел `success` с пустыми данными, проверить период, фильтры и наличие данных в Braze.

## Короткое резюме в одном абзаце

`Braze MCP` в этом окружении — это рабочий мост между агентом Codex и Braze API, позволяющий безопасно и структурированно читать данные из Braze через набор готовых функций. На текущий момент подтвержден доступ к основным read-only сценариям: campaigns, canvases, segments, events, custom attributes, KPI-series, content blocks, email templates, catalogs, scheduled broadcasts и части purchase analytics. Ограничения по текущему ключу явно видны для `preference centers` и `CDI integrations`, а часть остальных функций требует дополнительных идентификаторов для полной проверки.
